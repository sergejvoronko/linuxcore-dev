Debian maintainers do not break stable releases. The entire point of running Debian in your homelab is the guarantee that `apt upgrade` applies tiny, backported security fixes without touching core application logic. 

Yesterday, that rule shattered. Debian pushed rsync 3.5.0 directly into stable repositories to patch 33 separate CVEs. 

The vulnerabilities range from out-of-bounds reads to critical path-traversal exploits where a malicious sender can write files outside the designated destination directory. The architectural flaws ran so deep in the 3.2.x codebase that maintainers abandoned backporting entirely. 

Applying this rsync security update requires more than a blind package upgrade. A major version bump in a core utility will break unmaintained bash scripts and misconfigured cron jobs. You need a strategy to upgrade your homelab rsync backup security without silently corrupting your nightly syncs.

## Assessing Your Homelab Exposure

The risk profile of a Debian rsync CVE depends entirely on how your servers talk to each other. 

Running the rsync daemon (`rsyncd`) on public port 873 is leaving your server's front door wide open. If you expose the unencrypted daemon to the internet or even just a flat homelab IoT VLAN, you are highly exposed to unauthenticated memory corruption attacks. 

If you strictly tunnel rsync over SSH, your exposure drops but does not disappear. The vulnerabilities trigger when the receiver processes the file list sent by the remote machine. If your central NAS pulls backups from a compromised VPS or an untrusted container via SSH, the compromised node can exploit your NAS during the sync process.

You must audit your backup flow. Identify which machines act as receivers and update them first. 

## The Protocol Mismatch Problem

Rsync relies on a strict sender-receiver protocol negotiation. When you type `apt update && apt install --only-upgrade rsync` on your NAS, you upgrade the receiver to protocol version 33 (introduced in rsync 3.5.0). 

If your remote servers still run older protocol versions, the new 3.5.0 receiver will apply strict path validation rules to the older sender's output. In many edge cases involving symlinks and implied directories, this causes the sync to hard crash with a fatal error.

You must upgrade both ends of your backup pipeline simultaneously.

Use this bash snippet to check the installed rsync versions across your local network before you begin patching. It requires passwordless SSH access to your nodes.

```bash
#!/bin/bash
# check_rsync_versions.sh

NODES=("pve-node1" "nas-core" "docker-host" "nextcloud-lxc")

for node in "${NODES[@]}"; do
    version=$(ssh -o BatchMode=yes "$node" "rsync --version | head -n 1 | awk '{print \$3}'" 2>/dev/null)
    if [ -z "$version" ]; then
        echo "[!] $node: Connection failed or rsync not installed"
    else
        echo "[-] $node: $version"
    fi
done
```

Run this script. Any machine returning a version lower than 3.5.0 needs an immediate update.

## Script Compatibility and Broken Flags

Rsync 3.5.0 changes default behaviors to close security holes. These changes will break sloppy backup scripts.

### Strict Path Sanitization
Older versions of rsync allowed ambiguous trailing slashes in `--files-from` lists. Rsync 3.5.0 enforces POSIX-compliant path sanitization. If your automated scripts generate file lists with redundant slashes (like `/var/www//html/`), the new parser will reject them or strip them aggressively, which changes how directories nest on the target machine.

### Symlink Restrictions
The most severe CVEs involve symlink manipulation. A rogue sender could use symlinks to trick the receiver into overwriting system files outside the backup directory. Rsync 3.5.0 introduces `--munge-symlinks` by default in daemon mode and restricts `--copy-links` behavior when running as root. 

If your homelab backs up container volumes heavily reliant on internal symlinks, test your sync process manually. You will likely see `vanished file` or `symlink validation failed` errors in your logs. 

### Fixing Your Cron Jobs
Do not let your cron jobs fail silently. Update your scripts to capture the new exit codes. Rsync 3.5.0 introduces specific exit codes for path traversal rejections. 

Modify your bash wrappers to handle these failures explicitly:

```bash
#!/bin/bash
# secure_backup.sh

SOURCE="/data/app-configs/"
DEST="backup-user@nas-core:/volume1/backups/configs/"

rsync -aHz --delete-after --numeric-ids -e "ssh -T -c aes256-gcm@openssh.com -o Compression=no -x" "$SOURCE" "$DEST"
EXIT_CODE=$?

if [ $EXIT_CODE -eq 0 ]; then
    echo "Backup successful."
elif [ $EXIT_CODE -eq 23 ]; then
    echo "Partial transfer due to error (check symlink permissions)."
    exit 1
elif [ $EXIT_CODE -eq 35 ]; then
    echo "CRITICAL: Rsync 3.5.0 path validation failure. Check paths for illegal characters."
    exit 1
else
    echo "Rsync failed with code $EXIT_CODE"
    exit 1
fi
```

## Securing Docker Backup Pipelines

Many homelab administrators isolate their backup jobs inside Docker containers. If your `docker-compose.yml` pulls a generic `alpine:latest` or `debian:bookworm-slim` image to run a cron-based rsync script, you are running vulnerable binaries until you rebuild those images.

You must force a pull of the latest base images and rebuild your backup containers. Alpine patched rsync in their package repositories within hours of the Debian release.

Here is a modern, isolated Docker Compose setup for a dedicated backup puller. It mounts the SSH keys read-only and explicitly uses the updated Alpine image.

```yaml
# docker-compose.yml
services:
  backup-puller:
    image: alpine:3.20.3  # Ensure this specific patch level or higher
    container_name: homelab-rsync-agent
    restart: unless-stopped
    command: >
      /bin/sh -c "apk add --no-cache rsync openssh-client && 
      crond -f -l 2"
    volumes:
      - ./cronjobs:/etc/crontabs/root:ro
      - ./ssh-keys:/root/.ssh:ro
      - /mnt/backup-storage:/data:rw
    environment:
      - TZ=Europe/Berlin
    security_opt:
      - no-new-privileges:true
    read_only: true
    tmpfs:
      - /run
      - /tmp
```

This configuration achieves three things. It guarantees the latest binary execution via `apk add`. It prevents the container from modifying its own execution environment by mounting the root filesystem as read-only. It drops privileges effectively, mitigating local escalation if the rsync process is compromised.

## Verification and Rollout Strategy

Do not blindly push the update to all 15 nodes in your Proxmox cluster at once. 

Start with your primary backup destination. Run `apt update && apt install rsync`. 
Pick one low-priority client node, update it, and manually trigger a sync job using the `--dry-run` flag. Watch the output for skipped files or permission errors. 

If the dry run succeeds, remove the flag and run the actual transfer. Inspect the resulting file structure on the NAS to ensure trailing slashes or symlinks did not alter the directory tree. Only after verifying the physical files should you roll the update out via Ansible or your preferred automation tool to the rest of the network.

Debian forcing a major version into stable is a painful anomaly. You will likely spend an hour fixing scripts that have run flawlessly for five years. Patching these 33 CVEs is non-negotiable.
